# LLM 改进计划：v0.1 → v3.0

> 适用对象：自训练 LLM（nanoGPT 系），单机消费级 GPU（6GB 级）为主训练环境，必要时云算力补充。
> 日期：2026-09-20

---

## 0. 总览

| 版本 | 定位 | 核心目标 |
|---|---|---|
| v0.1（基线） | 可跑通的最小原型 | 端到端训练管线跑通，loss 正常下降 |
| v0.5 | 工程质量收敛 | 可复现、可观测、可回滚 |
| v1.0 | 能力基线确立 | 达到可用的小型语言模型，建立基准评估 |
| v2.0 | 能力跃升 | 数据规模/质量升级 + 架构升级，引入指令跟随 |
| v2.5 | 对齐与安全 | SFT → 偏好对齐，安全边界建立 |
| v3.0 | 生产级交付 | 推理优化、部署闭环、持续评测与迭代机制 |

原则：**每个版本必须有可量化的验收门槛；不达门槛不进入下一阶段的数据/算力投入。**

---

## 1. v0.1 → v0.5：工程质量收敛（把"能跑"变成"可信地跑"）

**目标**：消除训练管线的不确定性，后续所有对比实验才有意义。

关键改动：

- **配置管理**：训练超参全部外置为配置文件（LR、warmup、batch、seq len、参数量、数据版本），每次 run 生成唯一 run id。
- **可复现**：固定 seed；记录数据哈希、代码 commit、依赖版本；checkpoint 按 run id 归档。
- **可观测**：训练/验证 loss 曲线、梯度范数、LR 曲线落盘或接入 TensorBoard/W&B；异常（loss spike、NaN）自动告警并回滚到最近 checkpoint。
- **评估脚手架**：固化一套最小评估集（dev perplexity + 5–10 条人工抽检样例），每次训练结束自动产出报告。
- **冒烟测试**：改动代码后用 1% 数据跑短训验证管线未破坏。

验收指标：
- 相同配置两次 run 的 dev loss 偏差 < 1%
- 每次 run 可一键重放；checkpoint 损坏可恢复
- 任一改动前后有可比对的评估报告

硬件适配：本阶段全部可在 6GB GPU 完成（缩小模型/短训）。

---

## 2. v0.5 → v1.0：能力基线确立（第一个"可用"版本）

**目标**：在明确的数据范围内，训练出一个能力可度量的小型 LM，作为后续一切的基准。

关键改动：

- **数据**：
  - 明确目标域（通用文本 / 特定领域），清洗管线：去重（MinHash/exact）、质量过滤（启发式规则或 perplexity filter）、去污染（与评估集去重）。
  - 固定 data v1 版本号，token 量与模型参数满足 Chinchilla 近似（token ≈ 20 × params）。
- **模型**：从 nanoGPT 默认 GPT-2 级结构出发，收敛一版确定配置（如 100M–500M 参数，取决于算力预算）。
- **训练**：稳定化训练配置——cosine LR schedule、grad clip、bf16/梯度累积；至少训练到 loss 曲线平台区，不做"训到一半就交付"。
- **评估基线**：确立基准组合——dev perplexity + 2–3 个标准能力子集（如常识推理、阅读理解小样例），v1.0 的分数即此后所有版本的对比锚点。
- **采样与输出**：固化 decode 参数（temperature/top-p 默认档），输出质量人工抽检 ≥ 50 条并记录问题分类。

验收指标：
- dev perplexity 达到该数据/参数量级的合理区间（与同级开源小模型对比）
- 基准评估集分数可复测，人工抽检问题分类报告归档
- 完整训练日志与数据谱系（data lineage）可查

---

## 3. v1.0 → v2.0：能力跃升（数据与架构双升级）

**目标**：相对 v1.0 实现显著能力提升，这是最大的一次算力投入。

关键改动：

- **数据 v2**：规模扩大 3–10×；引入课程式配比（代码/数学/知识/对话分层配比与退火段数据）；中英文或目标语料比例显式控制。
- **架构升级**（逐项引入，每项独立消融）：
  - RoPE 替换位置编码（支持更长上下文外推）
  - GQA / SwiGLU / RMSNorm 等现代组件
  - 上下文长度 2k → 4k/8k（配合 rope scaling 或长文本数据）
- **训练效率**：FlashAttention、序列打包（packing）、梯度检查点，把同等算力下的有效 token 吞吐最大化。
- **指令微调引入**：构建 SFT 数据 v1（指令-响应对，来源分级：公开高质量集 + 自构建），在预训练模型上完成首版指令跟随能力。
- **评估扩展**：基准增加代码（HumanEval 级小样）、数学（GSM 级小样）、指令跟随抽检；与 v1.0 同测对比，量化提升幅度。

验收指标：
- 预训练 dev perplexity 较 v1.0 下降达到预期幅度（事先设定阈值，如 ≥15%）
- 每项架构改动有独立消融报告，无效改动回滚
- SFT 后指令跟随人工抽检通过率 ≥ 设定门槛（如 70%）

硬件适配：预训练主阶段建议云算力（A100/H100 短租）完成；6GB 本地仅做消融小模型与 SFT（LoRA/QLoRA）。

---

## 4. v2.0 → v2.5：对齐与安全

**目标**：让模型"好用且可控"，不仅是"会续写"。

关键改动：

- **SFT v2**：错误分析驱动——对 v2.0 抽检问题分类（幻觉、拒答不当、格式失控、指令丢失），定向补充数据；引入多轮对话格式与系统提示词约定。
- **偏好对齐**：构建偏好对数据（chosen/rejected，可用强模型蒸馏 + 人工修正），执行 DPO（优先于 RLHF，成本与稳定性更适合小团队）；可选后续探索 KTO/ORPO。
- **安全**：红队测试集（越狱、有害请求、隐私诱导）→ 安全 SFT/DPO 数据 → 复测闭环；输出侧增加可控的拒答风格。
- **幻觉抑制**：检索增强接口预留（RAG-ready），事实类问题训练"不确定时承认"的行为模式。
- **评估**：对齐前后对比——指令跟随、有用性、无害性三轴人工/模型评审；回归测试集防能力退化。

验收指标：
- 偏好评审中 v2.5 对 v2.0 胜率 ≥ 60%
- 红队集通过率显著提升且无显著能力回退（基准分下降 < 2%）
- 多轮对话与 system prompt 行为符合规范

## 5. v2.5 → v3.0：生产级交付（部署、效率与持续迭代闭环）

**目标**：模型从"实验室产物"变成"可持续运营的服务"。

关键改动：

- **推理优化**：
  - 量化（INT8/INT4，评估精度损失阈值）、KV cache 优化、投机解码（若吞吐敏感）
  - 目标：单卡/边缘部署的时延与吞吐指标明确（首 token 延迟、token/s）
- **服务化**：OpenAI 兼容 API 封装、流式输出、并发与限流、日志与脱敏。
- **RAG 与工具**：检索管线与函数调用（function calling）格式训练与联调，作为事实性能力的工程兜底。
- **持续评测体系**：线上样本回流 → 问题分类 → 数据 v3 增补 → 灰度训练 → 自动化回归评测 → 发布。形成固定节奏（如每 4–6 周一个数据/对齐迭代）。
- **发布管理**：模型卡（model card：能力边界、数据来源、已知风险）、版本化发布与回滚预案。

验收指标：
- 部署形态达到预设 SLO（延迟/吞吐/并发）
- 量化后基准分回退 < 1%
- 持续评测流水线跑通一次完整的"回流→迭代→发布"循环

## 6. 横向要素

### 6.1 评估体系（贯穿全程）
- 三层：自动基准（perplexity/标准集）→ 模型评审（成对偏好）→ 人工抽检（问题分类标签体系）
- 铁律：评估集与训练数据严格去污染；基准版本随数据版本归档

### 6.2 建议时间线（可按算力弹性伸缩）
| 阶段 | 建议周期 |
|---|---|
| v0.1 → v0.5 | 2–4 周 |
| v0.5 → v1.0 | 4–8 周（含一次完整预训练） |
| v1.0 → v2.0 | 6–12 周（最大算力投入） |
| v2.0 → v2.5 | 4–6 周 |
| v2.5 → v3.0 | 4–8 周 |

### 6.3 风险与对策
- **算力瓶颈**：预训练主阶段用云短租；本地只做消融/SFT/推理验证
- **数据质量不达预期**：数据 v2 先用小规模消融验证再全量投入
- **对齐导致能力回退**：回归测试集卡门，超阈值不发布
- **范围蔓延**：每版本验收门槛前置定义，功能请求进入下一版本 backlog

### 6.4 治理规范
- 一切对比结论必须来自同评估集、同 decode 配置的复测
- 数据集、代码、checkpoint、评估报告四者按版本强绑定
- 每次发布附 model card 与已知问题清单
